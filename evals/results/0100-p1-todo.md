## 1. Record the cassettes again

Each case once, on both models. About 2.5 million input tokens on each model, most of them the
questions over the 3,000 invoices (about 120,000 tokens a request, numbered, and about 3 requests
for a count): the recordings of 0.9.0 for these cases took 0.64 million on each. No question starts
once the run, both models together, has used 6 million.

```sh
GEMINI_API_KEY=… npm run eval:record -- \
  --cases policy-days,policy-seniority,policy-expense-cap,policy-travel-en,policy-sick-days,planted-instruction,budget-which-row,budget-lookup,budget-count,budget-sum-en,invoices-late,invoices-canceled-sum,invoices-lookup,invoices-customer-en,deck-south,deck-slide,sales-east,orders-refunds,orders-row,pdf-report,pdf-statement,pdf-statement-en,contract-late-delivery,chat-uploads,chat-dropped-file,invoices-xlsx-late,invoices-columns,budget-units \
  --results evals/results/0100-p1-record.json \
  --title "Evals: recordings of package P1 of 0.10.0" \
  --max-input-tokens 6000000 \
  --concurrency 2
```

Then T's 11 Flash recordings, if no one recorded them in the meantime:

```sh
GEMINI_API_KEY=… npm run eval:record -- --models gemini-3.8-flash \
  --cases log-failover,log-deploy,log-disk,log-hebrew,contract-penalties,contract-largest-en,contract-summary,diary-timeline,cleaning-sanctions,diary-planted-nothing,chat-log-orders \
  --concurrency 1
```

Check that every recording replays, without a key:

```sh
npm run eval:replay
```

A case that missed pass^1 or lost a fact when recorded is reported by the record run itself
(against `evals/baseline/0.9.0.json`): read `evals/results/0100-p1-record.md` before going on.

## 2. P1's live gate

Each case that sends a file whole, 3 times on each model (pass^3). About 7 million input tokens on
each model; no question starts once the run has used 16 million. The cases whose requests P1 did
not change need no live run for P1.

```sh
GEMINI_API_KEY=… npm run eval:live -- --k 3 \
  --cases policy-days,policy-seniority,policy-expense-cap,policy-travel-en,policy-sick-days,planted-instruction,budget-which-row,budget-lookup,budget-count,budget-sum-en,invoices-late,invoices-canceled-sum,invoices-lookup,invoices-customer-en,deck-south,deck-slide,sales-east,orders-refunds,orders-row,pdf-report,pdf-statement,pdf-statement-en,contract-late-delivery,chat-uploads,chat-dropped-file,invoices-xlsx-late,invoices-columns,budget-units \
  --results evals/results/0100-p1-live.json \
  --title "Evals: package P1 of 0.10.0, live" \
  --max-input-tokens 16000000 \
  --concurrency 2
```

The report, `evals/results/0100-p1-live.md`, figures the gates of the plan for each model. P1 passes
when, on each model:

- **Count questions answered right: 100%,** the inline Hebrew CSV (invoices-late, 750) and the
  inline Hebrew workbooks (budget-count, invoices-xlsx-late, 750) among them.
- **Citations inside what the tools showed: at least 90%,** and **answers with no citation
  recognized: at most 10%.**
- **Hebrew questions answered in Hebrew: every run.**
- **Facts lost against the baseline: none** (the run compares with `evals/baseline/0.9.0.json`).
- **Inline-table questions with no count, in one request: at least 90%,** and **inline-table count
  questions, requests at the median: at most 3.**

Also look, in the recordings and the live run, for a tool call over a table sent whole that got
"Unknown document_id" back: the frame line of such a table gives its document_id, and the fake
models take it from there, but only a live model shows whether it does.

The input tokens, the cached share and the latency of each question are in the same report; they
go to `docs/measurements.md` at the release (package E, part 2).

To write the report again, with notes under its title:

```sh
node evals/cli.mjs report --results evals/results/0100-p1-live.json --notes notes.md
```
