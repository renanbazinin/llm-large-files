GitHub npm

npm · MIT · Node 22.12+ · no runtime dependencies · adapters for Gemini, OpenAI-compatible endpoints and Claude

Let an LLM answer questions about files larger than its request limit or context window.

Your users upload a 50 MB log or a 900-page book. Your model connector accepts 10 MB per request and 1M tokens of context. This library sends the files that fit, turns the rest into a short card with tools to search and read them, and returns an answer that cites line numbers.

npm install llm-large-files
Quickstart How it works GitHub

It's a small library, not a framework: no model SDK, no server and no UI are required.

measured A live run, not the sample above: with gemini-3.8-flash on the Gemini API in November 2026, at version 0.1.0, a 5 MB log of 60,000 lines, over the 1M window, got the right root cause of an outage, citing the right lines (checked with grep), in about 60 s over 11 tool calls. It is one run, not a benchmark. Measured, with the conditions

fits
A file fits when it is within the room for whole files, 200,000 tokens by default, and within the request size. Its whole text goes into the first user turn, with its lines numbered. If every file fits, the question is one request, with no tools. A table sent whole still gets tools, so its counts and sums are exact.
too big
A card of a few KB takes the file's place: its format, size and line count, and what the profile found. For a log: level counts, the time range, the most frequent errors grouped by shape. For a book: an outline of headings with line numbers. Then the first 25 lines.
answer
The answer cites line numbers, like (app.log L1203). result.steps has one line per tool call. result.citations checks each citation against what the tools showed. result.usage sums every request.

quickstart

Ingest when a file is uploaded. Ask when the user asks.

files.ingest extracts the text of a file and indexes its lines, once. askGemini, or askWithFiles with any model, runs the loop for each question and returns the answer with what it did to get there.

Gemini on Vertex AI

With an access token from Application Default Credentials. google-auth-library is your application's, not a dependency of this package.

import { readFile } from "node:fs/promises";
import { GoogleAuth } from "google-auth-library";
import { createLargeFiles, FileDocumentStore } from "llm-large-files";
import { askGemini, vertexAi } from "llm-large-files/gemini";

const files = createLargeFiles({ store: new FileDocumentStore("./data/large-files") });
const userId = "user-42"; // the signed-in user: every call names its owner

// When a user uploads a file:
const doc = await files.ingest({ name: "app.log", bytes: await readFile("./app.log"), owner: userId });

// When they ask about it:
const auth = new GoogleAuth({ scopes: "https://www.googleapis.com/auth/cloud-platform" });
const endpoint = vertexAi({
  project: process.env.GOOGLE_CLOUD_PROJECT!,
  model: "gemini-3.8-flash",
  accessToken: async () => (await auth.getAccessToken())!, // asked for on each request
});
const result = await askGemini({
  files,
  endpoint,
  owner: userId,
  documentIds: [doc.id],
  messages: [{ role: "user", text: "What caused the outage, and when? Cite lines." }],
  onText: (delta) => process.stdout.write(delta), // optional: the answer as it streams
});

Any model

With another provider, name the model yourself. This pair is a sample: the Claude adapter and a DeepSeek endpoint have not been run live (Measured). The library assumes a window of 1M tokens: for a smaller one, set budget.contextTokens.

import { askWithFiles } from "llm-large-files";
import { openAiCompatible } from "llm-large-files/openai";
import { anthropic } from "llm-large-files/anthropic";

// OpenAI, Azure OpenAI, DeepSeek, LiteLLM, vLLM, Ollama, OpenRouter: anything that speaks Chat Completions.
const deepseek = openAiCompatible({ baseUrl: "https://api.deepseek.com/v1", apiKey: process.env.DEEPSEEK_API_KEY!, model: "deepseek-v4-pro" });
// Claude. `fallbacks` lets another model answer when a safety classifier declines the request.
const claude = anthropic({ apiKey: process.env.ANTHROPIC_API_KEY!, model: "claude-opus-5-5", fallbacks: "default" });

const withClaude = await askWithFiles({
  files,               // `files`, `doc` and `userId` are those of the quickstart
  owner: userId,
  model: claude,       // writes the answer
  explorer: deepseek,  // optional: a second model, of any provider, that searches and reads
  documentIds: [doc.id],
  messages: [{ role: "user", text: "What caused the outage, and when? Cite lines." }],
  onText: (delta) => process.stdout.write(delta),
});

withClaude.answered;  // false when the last reply had no text (a blocked prompt, a reply cut off before any text, a tool call that could not be read): show your own message
withClaude.usage;     // { requests: 5, inputTokens: 32662, cachedInputTokens: 6086, outputTokens: 750, thoughtTokens: 0, byModel: { … } }
withClaude.evidence;  // [{ tool: "read_document", documentId, document: "app.log", lines: [[34100, 34110]] }, …]
withClaude.toolTurns; // pass these back in `messages`, between this question and its answer: a follow-up then needs no new search

Gemini API or a gateway

With a key for the Gemini API, or your own proxy of Generate Content, swap the endpoint.

import { geminiApi, type GeminiEndpoint } from "llm-large-files/gemini";

const withKey = geminiApi({ apiKey: process.env.GEMINI_API_KEY!, model: "gemini-3.8-flash" });

// Your own proxy of Generate Content. Its headers are sent exactly as given.
const viaGateway: GeminiEndpoint = {
  url: "https://llm-gateway.example.com/v1/gemini:generateContent",
  streamUrl: "https://llm-gateway.example.com/v1/gemini:streamGenerateContent?alt=sse", // without it, no streaming
  headers: { "Content-Type": "application/json", Authorization: `Bearer ${process.env.GATEWAY_KEY}` },
};

The values are those of this page's sample question, recorded with a scripted model.

One line for each tool call, in order, with the loop's own notices among them. Show it as plain text, never as HTML: the steps quote what the model sent.

models

One loop, any model.

A provider is an adapter: one object that turns the loop's request into the provider's, and its reply back. These come with the package, and each posts JSON with fetch, with no provider SDK. Your application chooses the model: the package has no default.

One model to explore, another to answer

The model you name does both halves of the work on a large file: it explores the file, then it answers. Name a second model for the first half, and the many requests of a search go to it: it can be a cheaper or faster one. model gets what the tools returned and writes the answer in one request.

Left out or empty, nothing changes: one model does both. With askWithFiles the explorer can be of another provider. No such pair has been run live.

formats

What it reads.

Every format becomes text with numbered lines. Here is what each one keeps.

Text and Markdown

The file as it is, in UTF-8, UTF-16 or one of five older encodings. Markdown's # headings form the outline.

Logs

As text, plus a profile of the log: its levels, its time range, its most frequent errors.

JSON and JSONL

As text. Minified JSON becomes lines of at most 2,000 characters.

CSV and TSV

As text, a line a row. aggregate_table reads every row for exact sums, averages and groups.

HTML

The text a browser shows: headings, lists, tables as rows of cells, a link with its address. No scripts or styles.

DOCX

Headings, clause numbers as Word shows them, tables as rows of cells, then notes, comments, headers and footers.

Needs jszip

PPTX

Slides in the order of the slide show, each with its tables and its speaker notes.

Needs jszip

XLSX

Every sheet, a line a row with its row number in the sheet, and the values Excel last computed.

Needs jszip

PDF

The text layer, page by page, with tables rebuilt so that empty cells stay empty. Pages with a picture are marked.

Needs unpdf, and @cantoo/pdf-lib for the marks

Scanned PDF

Nothing to search. Taken only when PDFs are kept, which is off by default, up to 30 pages: the model looks at the pages. No OCR is built in.

Needs unpdf and @cantoo/pdf-lib

Refused, with a message for the user: binary and compressed files, Office files of before 2007, files with a password. More in PDFs and other formats.

What else it handles

Logs
Detected automatically. The card shows level counts, the time range, and the most frequent errors grouped by shape.
Books and documents
An outline of headings with line numbers: Markdown, "Chapter 12", numbered sections, Hebrew chapter titles.
Counting
Exact counts of matching lines, per hour, per code or per message shape, in one search. Exact sums over table rows, with no code run.
Citations
Answers cite line numbers, of files sent whole too. result.citations checks each against what the tools showed.
Every language
Search finds a Hebrew word with any prefix letter and words with or without accents, and splits a query the way each script writes its words.
One budget
It covers tokens and request bytes: files fit your context window and your connector's payload limit. It assumes 1M tokens and 10 MB: set budget.contextTokens for your model's window. Costs and limits
Reliability
Retries, waits on a silent model, recovery from a request too large, and a time limit on every store call. A question that fails throws DocumentsNotFoundError, DocumentStoreError, or a ModelRequestError whose kind ("rate_limit", "quota", "timeout", "context_overflow", …) tells you what to show the user. partialResultOf(error) gives what it found and paid for. Errors and reliability
Storage
In memory, on disk with expiry, or your own store (Redis, S3, a database). A document expires after 72 hours by default.
Older encodings
A text file that is not UTF-8 is read as Hebrew, Arabic, Cyrillic, Japanese or Western European text in its older encoding. Others are not recognized.

web app

Add it to a web app.

Node HTTP handlers for upload, list, get and delete. askStream gives typed events to send to the browser over Server-Sent Events. Documents belong to an owner, checked on every call by default.

Server routes

Four handlers for any Node HTTP server. The paths are yours: the library mounts none.

import express from "express";
import { createDocumentHandlers } from "llm-large-files/node";

const app = express();
// `files` is the quickstart's. getOwner names the signed-in user (here, set on req.user by your
// auth middleware): each upload is then theirs alone.
const documents = createDocumentHandlers(files, {
  getOwner: (req) => (req as typeof req & { user?: { id: string } }).user?.id,
});
app.post("/api/documents", documents.upload); // mount before express.json(): the body is the raw file
app.get("/api/documents", documents.list); // the user's documents, the oldest first (new in 0.99.9)
app.get("/api/documents/:id", (req, res) => documents.get(req, res, req.params.id));
app.delete("/api/documents/:id", (req, res) => documents.remove(req, res, req.params.id));

Browser upload

The body is the file as raw bytes, not a form. Uploads are taken up to 100 MB and kept for 72 hours by default.

const response = await fetch("/api/documents", {
  method: "POST",
  headers: { "Content-Type": "application/octet-stream", "X-File-Name": encodeURIComponent(file.name) },
  body: file,
});
const summary = await response.json(); // 201: { id, name, format, lines, estimatedTokens, expiresAt, … }; otherwise { error }

Chat route

The chat route is your code around askStream and writeSseEvents. This sample keeps no history.

import { askStream } from "llm-large-files";
import { writeSseEvents } from "llm-large-files/node";

app.post("/api/chat", express.json(), async (req, res) => {
  const stream = askStream({
    files, model: claude, // `claude` is the adapter of "Any model"
    owner: (req as typeof req & { user?: { id: string } }).user?.id,
    documentIds: [String(req.body.documentId)],
    messages: [{ role: "user", text: String(req.body.question) }],
  });
  await writeSseEvents(res, stream); // one SSE message per event; stops the question if the page leaves
});

The events of a question

In order: run.start is always first, and one of run.finish or run.error is always last.

run.start
Always first. It names the models and the documents.
plan
Which documents go in whole, and which are reached through tools.
request.start
A model request starts.
retry
That request failed and is sent again after a wait.
text
Answer text arrives. Joined, the deltas are the answer.
request.end
The request ended, after any retries.
tool.start
A tool call starts: its label, one line of plain text.
tool.progress
How far a whole-file read is.
tool.end
The call ended: its outcome, its step line, what it showed.
notice
What the question did that is not a request or a tool call.
run.finish
Always last when the question returns, with the result.
run.error
Always last when it throws: the error, in words for users.

Owners

Owner checks are on by default since 0.99.9. getOwner returns the ID of your signed-in user, and the library compares that one string: the sign-in is your application's. A request without a user is answered 401 "Sign in first.", and a document of another owner reads as missing, never as forbidden. Security

Uploads you do not trust

The handlers read each upload in your server's process. Ingest limits the text, the pages and the time of one file, and refuses the zip bombs and the PDFs built to hold a server that its checks recognize. It does not refuse every file built to hurt a server: a crafted PDF of 732 bytes ran a heap of 512 MB out of memory at ingest.

Read files you do not trust in child processes with a heap limit and a kill timer: pass createIsolatedExtractors().extractors to createLargeFiles, and give the server a memory limit too. Security · Deployment

limits

What it is not.

Three limits to know before you build on it.

Not a framework

It is one tool loop and a few adapters. No model SDK, no server and no UI are required. The loop offers the model only the library's own tools: a model that must also call your application's tools runs in your own loop, with files.prepare() and files.tools().

Not a promise that a model reads everything

A whole-file read can miss items: asked to list every one of 1,200 matching lines, one returned 492 and said that the result was incomplete. Exact counts come from search_document in exact or regex mode and from aggregate_table. A citation that checks out means the cited lines were shown to the model, not that the answer is right.

Not a sandbox for hostile files

Ingest limits one file and refuses what its checks recognize. It does not refuse every file built to hurt a server, and it does not filter or detect instructions written inside a file. Read uploads you do not trust in child processes with createIsolatedExtractors, and show answers and steps as plain text.

The card.

What the model sees in place of the file. This is the card of app.log, as the library wrote it for the sample question: 1,871 estimated tokens stand in for 3,260,485.

  1. Name and document_id The frame lines name the file. Every tool call takes the document_id.
  2. Format, size, lines, estimated tokens For a PDF, a PPTX or an XLSX, also its pages, slides or sheets.
  3. Not in your context The line that tells the model the file is not in its context, and what the tools can do with it.
  4. Log levels and time range For a log: the count of each level, and the first and last timestamps.
  5. The most frequent problems Grouped by shape: a number becomes <n>, an IP address <ip>. Each has its count and the line of its first occurrence. FATAL comes first, then ERROR, then WARN. The card shows the first 8 of the 15 that the profile keeps.
  6. The first 25 lines Numbered as read_document numbers them, each cut to 300 characters.

Six tools.

A model reaches a large file only through these, and only the documents of the question. A tool that fails returns an error the model can read, so it can try another way.

Each tool is declared only when it applies to the files of the question. The sample question was offered three: search_document, read_document and get_document_overview. A log holds no table. A whole-file read was not offered: app.log would take about 37 parts against a limit of 30, and the scripted model of that question has no part reader. When every file fits in the prompt, none is a table that the tools count and none has pages to look at, no tool is offered, and the question is one request.

The loop, request by request.

One loop serves every model. This is what it does with each reply, and what one question looks like from its first request to its answer.

Usage

result.usage sums every answered request of a question, in all and for each model (usage.byModel): the chat’s, the explorer’s, and the part reads of a whole-file read. It holds requests, inputTokens, cachedInputTokens, outputTokens and thoughtTokens. A request that failed and was sent again counts once.

The scripted model of the recording reports no tokens: inputTokens is 0 there, all 4 requests of the sample question are in unmeasuredRequests, and the library’s estimate stands in. Your provider’s bill is the record. usage is a close account of it.

Ceilings

By default: 12 chat requests, counting the answer, with tools in all but the last (limits.toolTurns). 8 calls run a turn (limits.callsPerTurn). Each document is read whole once (limits.wholeDocumentReads), and a question makes 2 whole-file reads in all (limits.wholeReadsPerQuestion).

The input tokens of a question have a default ceiling: the larger of 1,000,000 and toolTurns times the estimate of its first request, plus room for its whole-file reads (limits.inputTokens). limits.requests has no default. A question that reaches a limit ends with a request for the answer, written from what the tools returned so far. Costs and limits

The rules

  1. By default one turn runs at most 8 tool calls (limits.callsPerTurn), four at a time. A call past the eighth is answered “Not run”, and the model can send it again.
  2. Every result carries tool_turns_left, so the model can see its turns run out and answer in time.
  3. Every result stays in the conversation and is sent again with each later request. So the loop counts the room left, and cuts each result to its share of it, never below 600 characters.
  4. A call whose result is still shown in full is not run again. It gets a pointer to that result.
  5. A failed request is sent again when another try can help: HTTP 408, 409, 429 or 5xx, or no answer. Up to 3 more times, after 0.25 to 0.5 s, then 0.5 to 1 s, then 1 to 2 s, or after the wait the provider asks for. Never for a quota that ran out, or once text was shown.
  6. A request the provider refuses as too large is made smaller: older tool results become short stand-ins, and it is sent again, at most twice a question. When it is one of the first requests, the files are planned again for a smaller window, once. With Claude in the question, nothing is shortened. Not in the recording.
  7. When the tool turns or the room run out, one more request is made, and it must be answered in text. No limit throws.
  8. A second model, which can be a cheaper one, can make the tool calls. The other model then gets one request, and writes the answer from what the tools returned.
  9. Usage is summed for each model, and a question can have ceilings on its requests, its input tokens and its whole-file reads. The two notes under the ledger say which it has by default.

Reading a whole file, in parts.

Some tasks need all of a file and cannot be done by matching text: a full summary, a timeline, items that must be judged by meaning. For those the model can call analyze_whole_document. It reads the file in parts, with other model requests, and writes one answer from their notes.

30 parts at most
budget.maxMapChunks. A file that needs more is refused before any request. Most often it is not offered the read at all, and its overview says so. For the sample log: Not available for this file: it would take about 37 parts, and the limit is 30. Use search_document and read_document.
Four parts at a time
With the default budget a part has up to 100,000 tokens, so one read can cost about 3,000,000 input tokens. A read is priced before it starts, and refused, with the numbers, when it would pass a ceiling of the question.
Once a file, twice a question
By default each document is read whole once a question (limits.wholeDocumentReads), and a question makes 2 whole-file reads at most (limits.wholeReadsPerQuestion). A model that asks again is told to use the answer it has.
A part that fails
It is sent again, by the loop’s rule for failed requests. If it still fails, the read goes on and the answer says so (parts_that_failed). When the last step fails, the notes are the answer (notes_only): they were paid for.

Items, counted by code

With output: "items", each part lists the items it finds, each with its line and a quote. Code reads the replies, checks that each quote is on the line it names, and counts the items. No model merges them, so a read of 3 parts makes 3 requests.

An item whose quote is not found on its line is counted in unverified_items, not in total_items. In the recorded read the items are the scripted reader’s: the library checked each of the 172 quotes against its line, counted them by label, and kept the first 50.

Counting is the job of search

A whole-file read can miss items of a long list, even within its limits. Its own description says so. For a complete list or an exact count, the tool guide sends the model to search_document in exact or regex mode, whose total_matching_lines is exact, and to aggregate_table for the rows of a table. One read that missed items is on record: Measurements.

Looking at the pages of a PDF.

A large PDF goes to the model as text, and text cannot show a chart, a photo or a signature. Keep the uploaded PDFs, and the model gets a tool, view_pages, that hands it the pages it asks for. It is off by default, and it is not for reading text.

Measured: a chart the text cannot show

Asked which bar of a chart is tallest, gemini-3.5-flash-lite said from the text alone that it could not see the chart. With view_pages it looked at the page and answered correctly. For ten questions that the text answers, it looked at no page. One model, on the Gemini API, in November 2026, at version 0.3.0. Measurements · PDFs

Off by default
keepOriginals: ["pdf"] keeps the uploaded file, which takes disk space until the document expires and is swept. It also needs two optional packages: unpdf reads the text of a PDF, and @cantoo/pdf-lib cuts its pages.
When it is offered
For each PDF whose file is kept, when every model of the question can be sent the same kind of file. gemini() and anthropic() take a PDF by default, openAiCompatible() only with pdfInput: true. For a model that reads images and no PDF, imageInput: true sends one image a page, on Node 24 with unpdf 2 and @napi-rs/canvas. Looks at pages have been run live on Gemini only.
Five pages a look
One call shows 5 pages at most. With the default budget and Gemini, a question can look at 60 pages.
What a page costs
On Gemini a page costs about 530 tokens, whatever is on it: 532 for each of 1, 2, 3 and 5 A4 pages and 527 for a 16:9 slide, measured with gemini-3.5-flash-lite at version 0.3.0. openAiCompatible() counts a page at 1,000 tokens and anthropic() at 3,500: defaults to plan with (pageTokens), not measurements.
Scans
The library has no OCR. A PDF without text is refused unless PDFs are kept. Then a scan of up to 30 pages is accepted (scannedPdfPages): its text says, page by page, [No text on this page. It may be a scan, a photo, or a chart.] and the model reads it by looking.

install

Install.

One package with no runtime dependencies. The readers of PDF and Office files are optional packages: install the ones you need.

npm install llm-large-files
  • Node.js 22.12 or newer.
  • The package is ESM, and CommonJS code can require() it.
  • Its TypeScript types come with it.
